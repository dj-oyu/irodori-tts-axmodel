# pulsar2 ビルド環境への依頼 — リアルタイムTTS化に向けて

> 発信元: AX8850 実機（AI Pyramid Pro）での検証結果（2026-05-26）。詳細ログ: `runs/20260525T163624Z/REPORT.md`。
> ゴール: **AX8850 上でリアルタイムTTS**（text → wav）。現状パイプライン = `text →[torch CPU 条件付け]→ DiT(NPU) → DACVAE(NPU) → wav`。
> 実機側で「各段が NPU 上で SEGV せず動く・I/O 形状一致・latent_mask が runtime で生きている」までは確認済み。
> **次の一手は実機作業ではなく、ビルド設定（コア数・T・量子化処方）の再ビルド判断**。本書はその依頼。

## 実機で測った根拠（数値）
- DiT `kv_long_lm_cosu16`: **single core**、100ms/call（T=201）。dacvae_b0: **triple core**、189ms（T=119, 4.76s 音声）。
- 音声: 48kHz / hop=1920 / **25 frame/s**（T=119↔4.76s、T=201↔8.0s）。
- 1発話の DiT 呼出 = `steps × CFG分岐`。RTF（実時間比, T=201/8s音声）:

| 設定 | DiT呼出 | DiT時間 | RTF | 判定 |
|---|---|---|---|---|
| 40step + CFG(3分岐) | ~80回 | ~8–9s | **≈1.1** | わずかに遅い |
| 8step + CFG | ~16回 | ~1.8s | ≈0.22 | RT可・品質undercooked |

→ 律速は **DiT のみ**（dacvae/textenc は軽い）。本番品質(40step)で「あと1.5〜2x」。

## R1. DiT を multi-core(triple core) でビルド  【P0 / リアルタイムの本丸】
**根拠**: 実機で DiT は `Model type: 0 (single core)`、100ms/call。一方 dacvae は `Model type: 2 (triple core)` で同等規模を高速処理。DiT を triple core 化できれば 40step+CFG でも RTF≈1.1→**~0.4 に到達**しRT圏内。
**依頼**: kv_long の DiT を **triple core（3コア）構成**でコンパイル。
**受け入れ基準**: 実機 axengine ロードで `Model type: 2`、1call レイテンシが現状比で有意に短縮（目標 <40ms/call）。
**成果物**: `compiled.axmodel`（triple core 版）。

## R2. DACVAE を T=201 でビルド  【P0 / 連結のため】
**根拠**: `デプロイ設計.md` §「DACVAE 入力 z=(1,32,T) も T が DiT と一致必須」。実機実測で DiT 出力 v_pred=(1,201,32) に対し dacvae_b0 入力 z=(1,32,**119**)。**T が合わず end-to-end 連結ができない**。
**依頼**: DACVAE を **T_max=201** で1本ビルド（DiT と同じ実効長 T_real を渡し、末尾無音はトリム運用）。可変長 export が素直なら latent_mask 方式でも可。
**受け入れ基準**: 実機 axengine で入力 `z=(1,32,201)`、出力 `audio=(1,1,201×1920=385920)`。DiT 出力をそのまま投入して連結成功。
**成果物**: `compiled.axmodel`（T=201 dacvae）。

## R3. DiT 量子化処方の判断・再ビルド  【P0 / 品質】
**根拠（実機 dtype ゲートで検出）**: デプロイ DiT `kv_long_lm_cosu16` の量子化処方を build config + 実測 dtype で確認した結果、
- **FC 入力 U16 化率 0/245**（242×U8）。`node_cos` のみ U16。＝ **cosu16 処方**。
- 長文くぐもりを直した処方は `kv_long_allfcu16`（S16ops + cos U16 + **245 FC layer_names→U16** = true-A16, mel_L1 3.68→2.73）。
- つまり **latent_mask 版は allfcu16 の true-A16 処方ではなく cosu16 処方**。S16-on-FC は heuristic で U8 に降格（自前 pitfall #7/#8 通り）。
- これが **意図的な選択か silent drop かは実機側だけでは確定不能**。

**依頼（いずれか）**:
- (a) 長文品質を取るなら **latent_mask 入り export × allfcu16(245 FC layer_names→U16)** で再ビルド、**または**
- (b) cosu16 採用が意図なら、その根拠（品質許容/サイズ/速度トレードオフ）をドキュメントに明示。

**受け入れ基準**: 再ビルド時は `scripts/verify_activation_dtypes.py`（本検証で追加）で **FC入力 U16 coverage を実測 assert**（allfcu16 なら 245/245 近辺）。`verify_layer_dtypes.py` と併用。
**成果物**: 再ビルド `compiled.axmodel` + `quant/quant_axmodel.onnx`（dtype 検証用）。

## R4. 実機検証に必要な成果物の受け渡し  【P1】
実機にこれらが無く、sim≡NPU 等価(Ph2) と fp32 実聴が**ブロック中**。
1. **過去 sim 出力 `.npy`**（DiT v_pred / DACVAE wav、`full_loop_axmodel.py`/`dacvae_sim.py` の結果）
   → 同一入力を NPU 実行し **bit一致/SNR比較**で「sim の品質結論が実機に転送可能か」を判定。
2. **`build/dacvae_decoder.onnx.data`**（外部重みファイル。実機には 702KB のグラフのみで重み欠落 → fp32 ref が走らない）
   → DACVAE の fp32 vs NPU 等価比較・実聴の基準に必要。
3. （あれば）**fp32 リファレンス wav**（短/中/長 × 代表 seed）→ メモリ 1.9Gi の実機で 2GB torch を回さず実聴 A/B するため。

## R5. バケツビルド（任意・レイテンシ最適化）  【P2】
**根拠**: DiT/dacvae は T_max 固定 → 短文も最大長コストを払う。RT 体感は短文の応答速度が支配的。
**依頼**: 短(T~37)/中(T~110) の DiT・DACVAE を追加ビルド（R1 triple core を前提に）。
**受け入れ基準**: 短文発話で end-to-end < 1s 程度。

## 検証フィードバックループ（再ビルド後に実機で回す）
1. `ph0_inspect.py` — I/O 構造（core数・T・latent_mask 生存）
2. `verify_layer_dtypes.py` + `verify_activation_dtypes.py` — dtype coverage assert
3. `dit_smoke.py` / `dacvae_equiv.py` — NPU 実行 latency・liveness（+ onnx 重みが揃えば fp32 等価）
4. R2 連結後: `a_build_cond → b_sample(53入力 latent_mask 対応) → dacvae(T=201)` で実テキスト→wav・実聴
   ※ Stage A の 2GB torch はメモリ 1.9Gi でOOM危険 → 短文 or build host 生成 or 常駐化が前提（R4-3）。

## まとめ
- **RT 可否を決めるのは R1（DiT triple core）**。まずこれの効果を実機で測るのが投資対効果最大。
- **R2（dacvae T=201）が無いと end-to-end が繋がらない**。
- **R3 は品質の分岐点**（true-A16 を戻すか cosu16 で行くか）。
- R4 が来れば実機で sim≡NPU 等価と実聴まで到達できる。

## 暫定処置・留意（正直な限界）
- **#3 の triple-core は未実証**: build ログに `subgraph_npu_0] b1` が出るが意味未解決。NPU3 config が通った≠3コアで走る。**実機 axengine ロードで `Model type` を見るのが gate**（目標 <40ms/call vs NPU1 実測 103.9ms）。
- **#2 の calib は合成**: `build/calib_dacvae_201/` は T=119 実 calib を時間軸タイルで T=201 化（MinMax レンジ用途）。real T=201 latent 捕捉ではない。末尾領域の z 分布が異なれば帯域に影響しうる → **実用充分性は実聴で要確認**。
- **#1/#2 とも「PTQ build 受入充足」止まり**。最終品質判定は実機実聴（指標信頼度: per-step cosine < SNR < mel_L1 < 実聴）。

## 副次発見（事実記録）
- **triple-core レバー = config の `npu_mode: NPU3`**（dacvae=NPU3=Model type:2、DiT既定=NPU1=single から特定）。R1 は config 1行で試行可能。
- **FC の pulsar2 内部名は lm/非lm の quant_axmodel.onnx 間で集合一致**（順序のみ差・欠落0、実測）→ allfcu16(非lm由来)の 245 FC 名を lm グラフ(53入力)へ流用しても **silent-drop せず full coverage**。#1 config = `kv_long_lm_cosu16.json` の入力(53) + `kv_long_allfcu16.json` の layer_configs を合成（`pulsar_configs/kv_long_lm_allfcu16.json`）。
- **dacvae T=201 は 15GB ホスト RAM ではビルド不可**: frontend「Building onnx」段で 3回 OOM。`device:cuda:0` / `enable_onnxsim:false` / calib_size 縮小は**いずれも無効**（calib 前の段＝ハード RAM 壁）。`.wslconfig` で WSL2 RAM 15→27Gi に引上げて突破（swappiness だけでは swap 未使用のまま kill）。重い pulsar2 ビルドは 27Gi 要。
